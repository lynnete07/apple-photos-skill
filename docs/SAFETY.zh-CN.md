# 安全模型

Apple Photos 中的资产全局只保存一份，多个相册可以引用同一资产。“移出相册”和“删除资产”不是同一个动作。因此，本 skill 将所有全局删除视为破坏性操作。

## 信任边界

- 只通过 Apple 公开 PhotoKit API 访问 Photos。
- 不读取或修改 Photos 私有数据库。
- 除非用户另行要求云端操作，否则分析和执行全部留在本机。
- 不能根据归档状态、相册名称、收藏标记或配置文件推断删除授权。

## 修改前

Agent 必须：

1. 确认每个相册名称只对应一个相册。
2. 读取相册当前成员数量和标记数量。
3. 为本次范围建立一份明确的执行清单。
4. 先执行不带 `--apply` 的预检。
5. 遇到数量变化、动作冲突、相册重名、原件缺失或未经授权删除收藏时停止。
6. 取得本次合并破坏性操作的当前授权。

## 修改中

- 通过一次 PhotoKit 变更事务执行合并方案。
- 同时要求导出和删除时，先完成并验证所有选中原始资源，再开始删除。
- 保护收藏或未收藏中的相反子集。
- 权限被拒绝、iCloud 原件下载失败或导出不完整时停止，不反复重试。

## 修改后

- 核对受影响资产、相册是否存在、受保护子集和未解决动作。
- 分别报告 Photos 资产数与导出资源文件数，因为一个 Live Photo 可能产生两个文件。
- 明确说明删除资产已进入“最近删除”，恢复资产不会恢复相册结构。

## 恢复方式

Apple Photos 会在“最近删除”中暂时保留已删除资产。发生误删后应尽快从那里恢复。已经删除的相册可能需要手工重建。

## 数据最小化

请勿在公开 issue 中提交真实本地标识、文件名、GPS 坐标、人脸信息、个人路径或导出清单。请使用能够复现结构问题的虚构样例。
